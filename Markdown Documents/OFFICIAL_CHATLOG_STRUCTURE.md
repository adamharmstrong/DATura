# Official FFXI chatlog structure and DATura comparison

Analysis date: 2026-10-10.

## Scope and evidence

This document describes the chatlog implementation visible in the local PS2
decompilation and compares it with DATura's current implementation. The PS2
files identify themselves as autogenerated decompilation of version 972; they
are not pristine original source. Recovered class/function names are useful,
but some field types, signatures, global names, and call arguments are damaged.
Claims below are based on observable operations rather than treating every
recovered declaration as authoritative. They do not establish behavior in
every later retail version.

DATura source root: `C:/Users/nanob/source/repos/DATura/DATura/`.

## 1. Architecture

The official chatlog is a collection of cooperating components. Message
storage, the small scrolling log, expanded history, text input/channel
selection, event dialogue, and query menus have separate responsibilities.

The normal message path is:

```text
Text + message metadata
  -> AddString: conversion, control codes, explicit line breaks
  -> AddLogString / SetOneLineSqdata: glyph conversion and wrapping
  -> display-row circular buffer + larger buffered history
  -> normal log or expanded-history view
  -> shared menu frame + glyph renderer
```

Some event-message types take a separate event-controller path instead of
going straight through ordinary log insertion. Query menus are also separate
windows, even though they share text-rendering infrastructure.

## 2. Messages and display-row storage

`AddString` accepts text together with a `TK_DATAHEDDER`, indentation flag,
and conversion flag. `logDataHeaderCalc` builds richer log metadata, including
message type, color information, identifiers, and event/spooling flags.
Configuration flags can select chat types for spooled display.

Insertion can perform text conversion through `FsTextInput::convertToString`
and detect message call/chime controls. It recognizes explicit line breaks
including control byte `0x07`, CR, and LF. Certain event types are passed to
`CTkEventCtrl::AddData`.

For ordinary log messages, `AddLogString` calls `SetOneLineSqdata` to produce
wrapped glyph/control-code rows. Each row carries a metadata header and its
converted text. The code also appends serialized information to
`FsBufferedLog` and notifies the visible window through `AddLine`.

The in-memory display buffer has **100 circular slots of 0x200 bytes each**:
`Init` clears 0xc800 bytes, while the allocation routines wrap indices at 99
and clear one 512-byte record per allocation. Row metadata occupies 0x18
bytes in the insertion path. Eviction examines identifiers shared by related
rows rather than simply cutting a flat string at a newline.

**Important:** this is a display-row buffer, not a claim that the entire
official history is limited to 100 messages. One message can occupy several
rows, and older history exists behind the display buffer.

## 3. Text layout and rendering

The PS2 implementation converts text into glyph indices and embedded control
values. `SetOneLineSqdata` measures advancement through `SetIndent`, handles
indentation and inline color controls, and wraps at a 0x160-unit text width.
Its English-mode branch searches backward for a word boundary; other branches
contain punctuation/line-breaking rules. This is not just character-count
wrapping or splitting on spaces.

`TkDrawStringWithCtrl` interprets the converted sequence, changes colors when
it encounters control values, draws visible glyphs with `MojiIndexDraw`, and
advances using glyph metrics. A page/continue indicator can be drawn when the
caller requests it.

`LogDraw` walks backward through available rows and draws them from the bottom
upward. It uses **16-unit row spacing**, a left inset of four units in that
path, and a clipping/scissor rectangle. The shared menu system handles frame
and shape drawing; the log's text primitive is not the entire UI renderer.

Initialization uses a **352-unit text area** and resizes the window to
**366 units wide**. These are coordinates of the inspected PS2 UI, not modern
viewport pixels that should be copied without scaling/layout decisions.

## 4. Visible rows, contraction, and animation

The window constructor initializes an eight-row maximum, zero-row minimum,
and variable-height mode. Setters support fixed/variable behavior and minimum
and maximum visible rows. `SetDrawMaxLine` accepts values from four through
24 in this build; out-of-range input falls back to 24.

Window updates maintain separate quantities for text visibility, window
height, incoming-message scroll timing, and resize timing. New rows extend
the visibility budget, capped against the configured maximum. Height changes
are animated while preserving the bottom anchor. Scrolling can accelerate
when many rows are waiting and can jump to the newest rows for a sufficiently
large backlog.

Contraction is coordinated with other UI state. Event messages, spooled chat,
active-window state, and text editing affect the update path. Text input
reserves one row; event/spool overlays also reduce the ordinary log's drawable
area. A manual decrement request is processed separately from automatic aging.

`SetTimeForDECREMENTLINE` clamps the requested interval to at least three
seconds and converts it to timing units by multiplying by 60. The constructor
initializes an internal value of 0x14, but that is **not evidence of the final
player-configured default interval**. The complete configuration application
path was not resolved in this analysis.

## 5. Expanded history, channels, and event UI

`FsBufferedLog` provides storage beyond the visible-row ring. Its page code
contains temporary-file save/load operations. `CTkFullLog` uses log modes,
update counters, and older/newer storage retrieval to browse history. The
message-data layer tracks channel-specific counters such as say, shout, tell,
party, and linkshell. The exact overall history retention limit and behavior
across sessions were not established here.

`TkChat.cpp` is mainly the channel-selection/tell-target interface. The text
input/parser components are separate dependencies; it would be misleading to
describe `CTkChat` as the class that stores and renders the chat transcript.

Event dialogue is coordinated by event-specific controllers and windows.
`EventMessageRemoveALL` removes event data and destroys the associated event
menu; it does not simply erase all ordinary chat history.

Queries use the same glyph drawing helper but have their own window/control.
`XiEvent::CodeQUERY` adds the question and choices and applies selection/mask
information. `CodeQUERYWAIT` waits for a response and returns selection or
cancellation to the event interpreter.

## 6. Current DATura implementation

DATura's main chatlog implementation remains in
[npc_chat_window.h](C:/Users/nanob/source/repos/DATura/DATura/npc_chat_window.h).
It uses inline namespace state/functions, Win32 child windows, a read-only
Rich Edit transcript for selection/copying, and a separate input control.

The transcript is stored primarily as one `std::wstring`. The capacity helper
counts explicit newlines and trims the string to 100 such lines. Bitmap text
is wrapped when laying out/painting, so one retained logical line can produce
multiple visible rows without consuming multiple history slots.

The existing official-font path paints through
[ffxi_bitmap_font.h](C:/Users/nanob/source/repos/DATura/DATura/ffxi_bitmap_font.h).
It reads the English `font/moji` atlas from `ROM/119/51.DAT`; its verified
bitmap mapping is ASCII, with unsupported text using fallback behavior.

[ffxi_chat_assets.h](C:/Users/nanob/source/repos/DATura/DATura/ffxi_chat_assets.h)
reads `menu/windowps` group 6's authored color data from the same DAT. It
recreates a tinted backdrop rather than importing and executing the complete
official menu-shape renderer. Chat borders also contain custom painting.
Thus "uses official assets" does not mean every pixel or layout rule is
authored by the original menu system.

The log supports viewport-relative size, configurable fonts, an idle timeout,
row-by-row compaction, resize animation, wheel history scrolling, input recall,
and copying. Its GDI painting is also composited into the D3D9 backbuffer to
keep the UI visible across presentation modes.

Choice-menu rendering was extracted into
[query.cpp](C:/Users/nanob/source/repos/DATura/DATura/query.cpp) and
[query.h](C:/Users/nanob/source/repos/DATura/DATura/query.h). It shares chatlog
styling and font settings and now has independent backbuffer drawing. The
original query layout/cursor assets are not resolved; the current selection
marker is a text-based fallback. Conversation/event state remains with the
conversation controller and event runtime.

## 7. Differences at a glance

| Area | Inspected PS2 implementation | Current DATura |
|---|---|---|
| Architecture | Separate data, renderer, history, input/channel, event, and query components | Most chatlog state/behavior remains in one inline header; queries have a dedicated source file |
| Message representation | Typed metadata plus converted glyph/control sequences | Primarily a flat Unicode transcript |
| Display buffer | 100 wrapped-row slots with identifiers and metadata | 100 explicit newline-separated lines; wrapping happens afterward |
| Older history | Separate paged buffered history and expanded-log view | In-memory transcript scrolling; no equivalent paged-history system in the inspected chatlog |
| Text rendering | Glyph indices, metric advancement, inline controls and message colors | Shared bitmap atlas, simpler wrapping, mostly uniform transcript color |
| Geometry | Native menu rectangles and PS2 UI coordinates | Viewport-relative Win32 layout and configurable font size |
| Incoming scrolling | Separate row-scroll timing and backlog-dependent acceleration | Simpler transcript/bottom-scroll behavior |
| Contraction | Visibility budget coordinated with events, spool windows, editing, and menu state | Idle timer and compaction with simpler input/scroll guards |
| Event dialogue | Event controllers and overlay-aware log integration | Conversation controller/runtime presents messages through the chat window |
| Queries | Native query menu resource and cursor shapes | Separate module using chat styling and fallback layout/text cursor |
| Backdrop | Shared native menu-shape rendering | Partial asset-derived recreation with custom/fallback painting |

## 8. Implications for a future implementation

For closer behavioral fidelity, the most valuable changes would be to:

1. Separate message records/history from window rendering and input state.
2. Distinguish logical messages from wrapped display rows, retaining metadata
   and stable identifiers for both.
3. Preserve message types, colors, and inline formatting controls through
   decoding, wrapping, and rendering.
4. Model visibility, scroll animation, and resize animation separately, with
   explicit event/query/input coordination.
5. Add an expanded-history view backed by a history store rather than treating
   the small display buffer as the entire history.
6. Resolve native menu layout/frame/cursor resources before claiming exact
   visual reproduction.

Modern conveniences such as Unicode fallback, selection/copying, and scalable
viewport layout can remain deliberate DATura features. They should be
distinguished from verified official behavior rather than removed merely
because the PS2 renderer used a different mechanism.

This document is an analysis, not an implementation plan approval. No chatlog
behavior was changed as part of creating it.

## Implementation follow-up (2026-10-10)

DATura now wraps oversized words by glyph width, retains repeated spaces, and
recognizes CR/LF and control byte 0x07 as explicit breaks. Automatic chatlog
contraction pauses while a query window is visible. History storage remains
the existing logical-line transcript; the native metadata/row ring and paged
history described above are still future work.
