# Official FFXI query menus and DATura comparison

Analysis date: 2026-10-10.

## Scope and evidence

This document describes query menus in the local PS2 decompilation (version

pristine original source: names and control flow are useful, but some types,

## 1. What a query menu is

A query is a separate question-and-choice window, not a list of selectable
lines embedded in the chat transcript. It shares the menu system and glyph
renderer with other UI, but has its own state, items, cursor, input handling,
and answer. Event bytecode supplies the dialogue reference, initial selection,
and hidden-option mask; the event waits for the user's answer before continuing.

```text
Event opcode 0x24: message reference + default option + hidden-option mask
  -> resolve/process dialogue into QueryBuf
  -> create shared-menu query window
  -> add question and visible choices, retaining original option values
  -> draw menu and process navigation/confirmation/cancellation
Event opcode 0x25: wait for answer
  -> return selected value to event work state, or cancel the event
```

## 2. Event instructions and text parsing

In [XiEvent::CodeQUERY](C:/Users/nanob/source/repos/FFXI-PS2/src/main/actor/xievent.cpp:3350),
the operands at offsets 1, 3, and 5 are resolved through `getworkofs`:

| Operand | Meaning |
|---|---|
| Offset 1 | Dialogue-table entry reference |
| Offset 3 | Default selection in the original option numbering |
| Offset 5 | Bit mask: set bits hide the corresponding options |

The instruction uses request/completion flags while text processing populates
`QueryBuf`. It clears event-message presentation through
`EventMessageRemoveALL`; this is not an instruction to delete all ordinary
chat history. An existing query window is destroyed when needed.

After text processing finishes, the menu manager creates the query window.
The parser treats `0x07` as a line separator, `0x0b` as the transition from
question text to choices, and zero as the terminator. It has handling for
encoded text and control sequences rather than assuming plain ASCII.

Question segments are passed to `AddComment`; choices are passed to `AddItem`.
The option counter advances even when a mask bit hides an item. Thus hiding
an option does not renumber the event's answers. Each visible item keeps its
original one-based answer value internally; the default option is translated
into the corresponding visible cursor index.

## 3. Window, items, and cursor

[CTkMenuMng::CreateQueryWindow](C:/Users/nanob/source/repos/FFXI-PS2/src/main/tk/TkMenuMng.cpp:1616)
creates or reuses a query control and invokes `CreateDrawMenu` with a menu
resource reference. The symbolic resource name is unresolved in the inspected
decompilation; creation through the original menu system does not by itself
identify the installed DAT resource needed for a faithful port.

In [TkQuery.cpp](C:/Users/nanob/source/repos/FFXI-PS2/src/main/tk/TkQuery.cpp:228):

- `AddComment` clears existing items, converts the title using
  `SetOneLineSqdata`, and selects the color for message type `0x99`.
- `AddItem` allocates an item containing converted glyph data, glyph count,
  color, original answer value, and drawing coordinates.
- `SetCursol` adjusts the first displayed item so the initial selection is
  inside the visible portion of the list.
- `IsOK` exposes the answer state to the event interpreter.

The menu distinguishes the selected item index from the first displayed item
index and the item's event answer value. These are not interchangeable.

## 4. Rendering and layout

[OnDrawPrimitive](C:/Users/nanob/source/repos/FFXI-PS2/src/main/tk/TkQuery.cpp:360)
draws the converted question text and **at most three visible choice items**.
It calls `TkDrawStringWithCtrl`, the same glyph/control-code helper used by
the chatlog. It obtains the selection cursor shape from the menu controller
and draws it through `YmMenuShape::Draw`; the cursor is not a literal `>`
prefixed to the selected text.

[OnDrawCalc](C:/Users/nanob/source/repos/FFXI-PS2/src/main/tk/TkQuery.cpp:403)
gets placement from the menu resource's window and button rectangles. The
question origin is offset by four units horizontally and seven vertically
from the window origin. Choice origins come from button positions. The code
also updates available scroll-control state using the item count and first
displayed item index.

The shared menu renderer supplies the surrounding shapes/frame. Consequently,
the event script alone does not specify the complete appearance: reproducing
it requires the menu layout, frame/background, cursor, glyph assets, and
appropriate coordinate scaling.

## 5. Navigation, sounds, and cancellation

[OnKeyDown](C:/Users/nanob/source/repos/FFXI-PS2/src/main/tk/TkQuery.cpp:452)
supports single-row movement and page movement of up to three rows, as well
as button-index-based selection. Ordinary up/down branches stop at list ends
instead of wrapping from the last item to the first. Cursor and first-visible
indices are adjusted and clamped as required.

Moving the selection calls `YmSePlayCursor`. A cancellation request is accepted
only when `CliEventCancelFlag` permits it: accepted cancellation sets answer
`0xff` and calls `YmSePlayCancel`; a disallowed request calls `YmSePlayBeep`.
These are verified sound-function calls, not resolved sound-file identities.

Confirmation returns the selected item's stored answer value.
[CodeQUERYWAIT](C:/Users/nanob/source/repos/FFXI-PS2/src/main/actor/xievent.cpp:3508)
then handles the result:

| Answer state | Event behavior |
|---|---|
| Zero | Keep waiting |
| Selected one-based item value | Store value minus one in `_Work_Zone`; destroy query UI and clear query flags |
| `0xff` cancellation | Store `0xfe`, destroy query UI, clear flags, and set event-end/cancel flags |

Choosing a visible option whose wording is "No" or "Not now" is a normal
selection and can run an event branch. It is not necessarily equivalent to
pressing the cancel control.

## 6. Concrete portal example

Heaven's Tower event 83 uses dialogue entry 80 from installed
`ROM/25/51.DAT`:

```text
Do you want to warp to the first floor?
  Yes.
  Not now.
```

The event uses query opcode `0x24` followed by wait opcode `0x25`. The choices
are original event values zero and one after the interpreter's one-based-to-
zero-based conversion.

This menu belongs to the upper-floor return portal. The inspected ground-floor
Tower-to-Walls event 41 and Walls-to-Tower event 86 start their warp sequences
without this confirmation menu. Windurst Walls' Komulili NPC has a separate
"Warp to Port Windurst?" menu with "Yes." and "No."; it should not be confused
with the Tower entrance circle.

See also [portal research](HEAVENS_TOWER_PORTAL_RESEARCH.md).

## 7. DATura's current architecture

[query.cpp](C:/Users/nanob/source/repos/DATura/DATura/query.cpp) contains the
choice-window implementation extracted from `npc_chat_window.h`.
[query.h](C:/Users/nanob/source/repos/DATura/DATura/query.h) exposes the existing
`NpcChatWindow` API and query display state. This is a dedicated source module,
but not an independent native-menu framework: it still depends on chatlog
font, backdrop, wrapping, sizing, and UTF-8 conversion helpers.

The query renderer receives already-decoded question and option strings.
It does not itself interpret event instructions, option values, or cancellation.
Those responsibilities remain distributed among:

- [npc_event_runtime.cpp](C:/Users/nanob/source/repos/DATura/DATura/npc_event_runtime.cpp:241):
  opcode `0x24` records the dialogue reference, default option, mask, and
  waiting state; `0x25` waits for a choice.
- [npc_conversation_controller.cpp](C:/Users/nanob/source/repos/DATura/DATura/npc_conversation_controller.cpp:54):
  splits the dialogue using `SplitChoiceText`, preserves original option
  values, and maps the default into a visible selection index.
- [main.cpp](C:/Users/nanob/source/repos/DATura/DATura/main.cpp:4021):
  controls navigation, selects the original option value, hides the menu,
  and resumes the conversation/event.

`NpcEventRuntime::SelectChoice` stores the selected value in `state.zone[0]`
and clears the pending-choice state. Preserving event answer values despite
hidden options is already part of DATura's controller path; it is not a
missing feature merely because `query.cpp` itself only stores visible strings.

## 8. DATura rendering and input differences

DATura creates a Win32 child window and paints with GDI. It reuses
`FFXIBitmapFont` and the asset-derived chat backdrop when available, with
fallback font/backdrop behavior. `DrawChoices` also composites the query into
the D3D9 backbuffer independently of whether the chatlog is visible.

Current layout is computed from viewport size and chatlog settings. The menu
sits above the visible chatlog or near the bottom when the log is hidden. It
reserves two rows for a nonempty question. In the bitmap-font path only the
first two wrapped question lines are drawn.

Up to **12 choices** are displayed, with the first visible choice computed to
keep the selection approximately centered. Choices are single-row strings.
The selected choice is prefixed with `> `, and custom horizontal border lines
are painted. Original PS2 query layout/cursor assets have not been resolved.

The choice window's procedure currently handles painting and teardown, not
mouse activation or key selection. Keyboard navigation is handled by the main
application. Its up/down conversation-choice helper uses modulo arithmetic,
so it wraps at the ends. Escape ends the conversation in the current main
handler; it does not implement the PS2 `CliEventCancelFlag` gate, answer
`0xff`/work-value `0xfe` path, or corresponding menu cancellation sound.
The query module itself contains no cursor/cancel/beep sound dispatch.

## 9. Comparison summary

| Area | Inspected PS2 behavior | Current DATura |
|---|---|---|
| Event operands | Dialogue reference, default, hidden mask | Corresponding operands are recognized by the event runtime |
| Hidden choices | Hide visually; retain original answer numbering | Controller preserves original option values and maps default selection |
| Visible list | Three choice rows; scroll/page navigation | Up to 12 rows; selection-centered visible subset |
| Ordinary up/down | Stop at ends | Main conversation helper wraps at ends |
| Layout | Original menu window/button rectangles | Viewport/chatlog-derived calculations |
| Question conversion | Native converted glyph/control sequence | Decoded UTF-8 converted to Unicode; simpler wrapping, two-row question display |
| Cursor | Menu cursor shape | Literal `>` marker |
| Colors/frame | Native message color and shared menu resource rendering | Chatlog styling, mostly uniform text color, custom border |
| Input ownership | Query/menu controller handles button actions | Main application controls selection; query child handles painting |
| Cancellation | Event permission gate, explicit answer/result flags | Escape ends the current conversation; not equivalent to the native query protocol |
| UI sounds | Cursor, allowed-cancel, and disallowed-cancel sound calls | No equivalent dispatch in the query module |
| Presentation | Native menu draw path | Win32/GDI plus independent D3D9 backbuffer compositing |
| Portal use | Portal event must execute query instructions | Creating `query.cpp` alone does not wire portal event 83 into local zoning |

## 10. Verification and remaining work

The current DATura module compiled in the Release build. Its query smoke test
checked shared asset loading, selection clamping, painting without a chatlog,
empty-menu hiding, and window teardown. It did not establish pixel-exact
matching, native event cancellation fidelity, UI sound fidelity, or successful
execution of every portal event.

For closer fidelity, resolve the native query menu resource and cursor;
implement three-row list/page behavior and native navigation boundaries;
preserve formatting/color controls; model cancellation permission and results;
and connect verified UI sound calls to the appropriate assets. Keep rendering
and event-answer ownership distinct so visible indices are never mistaken for
original answer values.

This document records analysis only. No query behavior was changed while
creating it.

## Implementation follow-up (2026-10-10)

DATura now displays three choice rows with a separate first-visible index.
Ordinary navigation stops at list ends and Page Up/Down move up to three
choices. Selection changes retain the current scroll position until the cursor
leaves the visible rows. Questions use measured wrapped height rather than a
two-row cutoff, and backbuffer painting clips to the query rectangle.

The asset-backed QueryTests exercise scroll boundaries, long-word wrapping,
spacing and explicit breaks, longer-question layout, painting, and teardown.
Native cursor resources, sounds, formatting controls, and cancellation protocol
remain unresolved. Page movement currently changes selection by three and then
ensures visibility; the PS2 page helpers also shift the first-visible index
independently, so this is not an exact port of every page-navigation case.

## Menu/cursor modules (2026-10-10)

`DATura/menu.h` and `menu.cpp` now own reusable window/button rectangles,
backdrop/frame painting, and selection-cursor placement. `menu_cursor.h` and
`menu_cursor.cpp` own cursor location, resource offsets, scale, visibility,
shape frames, explicit animation ticks, and clipped drawing. The design follows
`CTkDrawCtrlCursol::LocateCalc`, `ShapeInit`, and `ShapeCalc` in
`TkMenuCtrlData.cpp` and the separate shape drawing in `TkQuery.cpp`.

Queries no longer prepend a text `>`: a separate geometric pointer is drawn
at the selected button. That polygon and the frame are explicit fallbacks,
not recovered retail artwork. Existing asset-derived backdrop loading remains
in use. Frame advancement models the reset-to-three/negative-countdown pattern
using four explicit UI ticks per frame; original global timing configuration
and native shape/texture decoding are not ported. Animation is opt-in and the
query fallback is static. Tests cover resource offset positioning, frame
advance/wrap, menu geometry, clipped pointer painting, and the query smoke path.
